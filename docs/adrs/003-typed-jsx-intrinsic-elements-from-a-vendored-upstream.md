# ADR-003: Type `JSX.IntrinsicElements` by deriving it from a vendored upstream, behind an Inkline-owned alias

Date: 2026-07-29 · Status: Accepted
Deciders: Project owner · Informed by: internal tracker UXF-71 (friction audit), UXF-90 (RFC + measurements), UXF-133 (implementation)
Supersedes: — · Superseded by: —

Resolves the first item ADR-001 left in "Explicitly still undecided". ADR-001 is unchanged and still
Accepted; its ordering of diagnostic work stands, subject to the revisit trigger it wrote for exactly
this event ("a decision lands on typing the authoring surface").

## Context

`.ink.tsx` markup had no types. `JSX.IntrinsicElements` was `[elemName: string]: any`, so
`<div className="x">`, `<button onClik={…}>`, `<input disabled="yes-please">` and `<notatag />` all
compiled clean and surfaced only when the generated output was run in a browser. This was the
friction audit's highest-ranked _absent_ diagnostic: the compiler stayed quiet.

Writing a full `IntrinsicElements` from scratch is real work with a permanent maintenance tail — the
HTML and SVG attribute surface plus the DOM event map is thousands of lines that must track the
platform. Three options were measured on the repo's own authored corpus (UXF-90):

- **Borrow React's** (`@types/react`). First pass: 20 errors across the corpus, and a 56-line
  compatibility shim to reconcile React's DOM-property naming (`className`, `htmlFor`) with the
  attribute names Inkline emits.
- **Borrow Solid's** (`solid-js`). A 34-line shim and one property name (`indeterminate`) to
  reconcile. Solid's surface is attribute-named (`class`, `for`), which is what Inkline's targets
  emit, and its signal-and-JSX authoring model is the closest neighbour to Inkline's.
- **Stay `any`.** Zero cost, zero benefit; keeps shipping the silence.

Solid's surface won on the measurements. _How_ to obtain it was a second question, and the first
implementation got it wrong: it added `solid-js` to `@inkline/core`'s `dependencies` and imported the
types from the package. That was rejected. `solid-js` is a runtime package, and `@inkline/core`'s
entire purpose is to ship no runtime — the compiler erases every reference to it. A runtime framework
in the dependency tree of a package that has none would be installed by every consumer, appear in
every audit and lockfile, and imply a framework relationship that does not exist. Inkline compiles
_to_ Solid as one of seven targets; it is not built on it.

A types-only replacement was looked for and none qualified: `@michijs/htmltype`, `dom-expressions`
and `jsx-dom` all ship JavaScript; `@types/web` is types-only but describes the DOM lib, not a JSX
namespace; `@types/react` is types-only but was already rejected on the measurements above.

The measured safety level was also part of the decision, not a discovered afterthought. Of twelve
deliberate authoring mistakes, this surface catches eight and structurally cannot catch four:
hyphenated attribute names (TypeScript exempts non-identifier JSX attribute names from
unknown-property checking, which is what makes `data-*` authoring work at all), component prop typos
(`InkComponent` carries `[attr: string]: any`), invalid members of open string unions upstream
declares as `… | (string & {})`, and unknown `$`-prefixed compiler directives.

## Decision

Derive `JSX.IntrinsicElements` from a **vendored verbatim copy** of Solid's element types —
[`core/core/src/vendor/jsx-intrinsics.d.ts`](../../core/core/src/vendor/jsx-intrinsics.d.ts), a single
`.d.ts`
whose only import is `csstype` — reshaped through a single Inkline-owned alias in
[`core/core/src/jsx-runtime.ts`](../../core/core/src/jsx-runtime.ts):

```ts
type Inklinified<T> = { [K in keyof T]: Omit<T[K], InklineOwnedKeys> & InklineOwned };
```

`@inkline/core`'s only remaining dependency is `csstype`, which is types-only by construction: the
published package contains `index.d.ts` and no JavaScript at all.

Four commitments come with it:

1. **The alias is the contract, not the upstream.** The public shape is "upstream element attributes,
   minus the keys Inkline redefines, plus `InklineOwned`". Replacing the vendored copy with a
   generated Inkline-owned surface later is one `extends` clause, invisible to authors. That claim is
   no longer theoretical — moving from the `solid-js` package to the vendored copy cost exactly that
   one line and zero author-file edits.
2. **The vendored copy is never edited.** It is generated by
   [`core/core/scripts/generate-jsx.mjs`](../../core/core/scripts/generate-jsx.mjs) from
   [`manifest.json`](../../core/core/src/vendor/manifest.json), the single input. The MIT attribution,
   the pinned version, the body checksum and the re-sync procedure all travel inside the header of
   [`jsx-intrinsics.d.ts`](../../core/core/src/vendor/jsx-intrinsics.d.ts) rather than in a sibling
   file, so they cannot be separated from the copy they describe. It is excluded from `vp fmt` so the
   body stays byte-identical and re-syncing stays a plain `diff`. It is _not_ excluded from lint,
   because that list also gates type-checking and this file is the surface under test.
3. **`InklineOwned` is where Inkline overrides upstream**, and nowhere else: `ref` is Inkline's
   `{ current }` object, `children`/`key` are compiler-opaque, `indeterminate` is a DOM property with
   no HTML attribute, and every `` `$${string}` `` key stays open so directives are unconstrained by
   construction.
4. **Component props stay untyped.** `InkComponent`'s `[attr: string]: any` is explicitly out of
   scope. It is a much larger change with a different blast radius and gets its own decision.

The 101 compiler fixtures are checked as part of this: they are no longer excluded in
`core/compiler/tsconfig.json`, and no longer ignored by the root `vite.config.ts` — that
`ignorePatterns` list gates the type-check path too, which is why excluding them had silently kept
them out of CI. The fixtures are the control that catches a bad re-sync.

## Consequences

**Good.**

- The corpus that motivated this is now checked: 170 authored `.ink.tsx` files, and the repo-wide
  type-check corpus grows from 611 to 717 files. On the compiler fixtures the typed surface is a net
  improvement of 10 errors against the `any` baseline — every implicit-`any` event parameter is now
  inferred — with zero new errors introduced.
- Event handlers get real event objects. `e.currentTarget` is the element, not `any`, which is where
  most of the day-to-day value lands.
- Editors gain attribute autocomplete on every intrinsic element, from the same types.
- **`@inkline/core` still depends on no runtime package.** Its one dependency, `csstype`, ships no
  JavaScript. A consumer's lockfile gains a types-only entry and nothing else.
- The safety level is pinned by test, not by prose:
  [`jsx-runtime.probes.test.ts`](../../core/core/src/jsx-runtime.probes.test.ts) asserts all twelve
  probe outcomes. A re-sync that stops catching one of the eight fails, and one that starts catching
  one of the four fails too — so the documented blind spots cannot go stale.

**Bad.**

- **4,253 lines of third-party code now live in the repo.** Vendoring trades a dependency edge for a
  maintenance obligation: nothing updates the copy automatically, so an upstream correction only
  arrives if someone runs the re-sync. The pinned header, the README procedure and the probe suite
  exist to make that cheap and loud, but they do not make it happen.
- **`@inkline/core`'s published declarations grow from ~1.7 kB to ~163 kB** (21.5 kB gzipped),
  because the element surface is now inlined into `dist/jsx-runtime.d.mts` rather than referenced.
  This is types-only weight — install size and editor parse time, not runtime bytes.
- **It can turn green consumer builds red.** That is the intent, but it is a cost paid by anyone who
  relied on the untyped surface. Mitigated, not removed, by a documented `jsxImportSource` shim that
  restores the old behaviour while errors are worked through.
- **Four of twelve mistakes still pass.** The surface is a real improvement, not a guarantee, and the
  gap most likely to bite — component prop typos — is the one deliberately left open. Presenting
  "typed JSX" without that caveat would overstate what authors actually get.
- **The fixtures are now a gate.** Adding a fixture that does not type-check fails CI, which is the
  point, and is also new friction on a corpus whose job is to be weird.

**Neutral.**

- `@inkline/core` still ships no runtime and the compiler still erases every reference to it. Nothing
  about the output changed; this is an authoring-time and editor-time change only.

## Revisit triggers

Written now, before the consequences are known:

- The vendored surface diverges from the attribute surface Inkline's targets emit — more than a
  handful of `InklineOwned` overrides accumulate, or a re-sync breaks the probe suite twice. Then
  generating an Inkline-owned surface outranks borrowing one.
- The re-sync does not happen. If the pinned version falls more than two minors behind upstream with
  no deliberate decision to stay, the procedure is not working and needs automation or replacement.
- Real reports arrive of the four blind spots costing time. The component-prop one is the likely
  candidate and is a separate decision; the other three are structural and would argue for compiler
  diagnostics instead.
- The declaration size becomes a complaint. 163 kB of `.d.ts` is defensible for what it buys; if it
  measurably slows consumer editors, a trimmed or generated surface outranks the full copy.
- A consumer needs the `jsxImportSource` escape hatch for longer than one minor cycle. Then the
  migration cost was underestimated and the rollout, not the decision, needs rework.
